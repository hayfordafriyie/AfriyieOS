Install scripts are now returned, not merely excluded
====================================================

THE GAP THIS CLOSES, named in the previous round and left open.

A real busybox package showed that Alpine's install scripts live in the
same tar as the payload, as dot-named files at the archive root:
.post-install, .post-upgrade, .trigger.

Excluding them from the FILE LIST was necessary and not sufficient. A
package manager that installs busybox and never runs .post-install has
installed a package that does not work, and would have reported success.

They are now collected during the same single walk of the tar that finds
.PKGINFO, with their CONTENTS, and exposed through af_pkg_info_t. The
test asserts the bytes, not just that a name was recorded — a reader that
noted a script existed without keeping it would pass every structural
check and be useless.

--- real packages, with their scripts ---
  === the reader against real Alpine packages ===
    ok    busybox                1.36.1-r31         7 files  21 dirs  deps  1  leaked 0  scripts 3 (post-install, post-upgrade, trigger)
    ok    ca-certificates        20260413-r0      150 files  16 dirs  deps  3  leaked 0  scripts 2 (post-deinstall, trigger)
    ok    musl                   1.2.5-r3           1 files   1 dirs  deps  0  leaked 0  scripts 0
    ok    ncurses-terminfo-base  6.4_p20240420-r2  39 files  13 dirs  deps  0  leaked 0  scripts 0
    ok    zlib                   1.3.2-r0           1 files   1 dirs  deps  1  leaked 0  scripts 0
  
    5 real package(s) read, none leaked metadata

busybox's three match exactly what Python's tarfile sees in the same
file. ca-certificates carries two of its own. Three of the five carry
none, which is the case that matters for a different reason: a reader
that invented a script, or crashed without one, would be wrong there.

NOT YET DONE, and named rather than implied: the scripts are returned but
nothing RUNS them. Executing them needs the sandboxed-command machinery
that arrives with the package manager, and an install script is untrusted
code from a third party — running it is a capability decision, not a
parsing one.

Also recognised and deliberately not executed: dot-named root entries
that are not in apk-tools' closed list of script names. They are counted
rather than ignored, so "we ran everything" is a claim the reader can
support or not.
