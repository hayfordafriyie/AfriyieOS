# AfriyieOS v0.1.0 — *Seed*

**Released:** in development
**Target:** x86_64 (PC, UEFI)
**Theme:** boot and display

---

## Summary

The first milestone. AfriyieOS becomes code that runs on bare metal rather than
a document: firmware loads the boot bridge, the boot bridge builds a normalised
description of the machine, the kernel takes over, initialises the CPU, brings up
a framebuffer and draws a real interface to it.

## What works

### Boot

- **UEFI boot bridge** (`boot/uefi/`) — loaded by firmware from
  `EFI/BOOT/BOOTX64.EFI` on the EFI System Partition
  - disables the firmware watchdog so a slow boot is not reset underneath itself
  - locates the Graphics Output Protocol and records the linear framebuffer,
    including the **stride**, which is the single most common cause of a skewed
    first image
  - reserves physical memory at `0x100000` with `AllocateAddress`, so firmware
    fails loudly rather than relocating the kernel to somewhere it was not linked
  - normalises the UEFI memory map into `af_memory_region_t`
  - marks any region covering the framebuffer as `AF_MEM_FRAMEBUFFER`, so the
    PMM can never allocate video memory
  - calls `ExitBootServices` in a retry loop with a refetched `MapKey`
  - jumps to the kernel with paging off and interrupts disabled

- **Kernel entry** (`kernel/arch/x86_64/entry.asm`) — installs its own stack,
  zeroes `.bss`, and calls `kmain`

- **CPU initialisation** — a 64-bit GDT with the final selector numbering
  (`0x08`, `0x10`, `0x18`, `0x20`, `0x28`) and a 256-entry IDT with 48 real
  stubs. The 8259 PICs are remapped from `0x08` to `0x20`; without that, the
  first timer tick arrives as a double fault.

### Display

- **Framebuffer** — surface initialisation with format and pitch validation,
  and packed-RGB conversion to native pixels for `RGBX8888`, `BGRX8888` and
  `RGB565`
- **Drawing primitives** — clipped pixel, rectangle, outline, horizontal and
  vertical line, vertical gradient, alpha blending, rounded rectangles and a
  drop shadow
- **Text** — a complete 8×16 printable-ASCII bitmap font with scaling, and
  measurement for centring
- **Splash screen** — a responsive boot screen: a centred card in landscape
  (desktop) and a stacked layout in portrait (phone). This is the first version
  of the breakpoint rule the Shell uses from v0.8.

### Diagnostics

- **Serial console** — COM1 at 115200 8N1, with a scratch-register probe so a
  machine without a UART cannot hang the kernel waiting on a transmitter that
  never drains
- **Structured logging** — elapsed-time prefix, level filter, module tag,
  timestamped, with a swappable output sink
- **On-screen console** — the boot log is mirrored to the screen, so a developer
  without a serial cable can still see it
- **Panic path** — interrupts off first, recursion guard, then reason, file,
  line, function, build identity and a full register dump including `CR2` for a
  page fault and eight raw stack words. It never reboots: the fault state is the
  entire value of the crash.

### Tooling

- **`tools/build_toolchain.sh`** — builds `x86_64-elf` and `aarch64-elf` GCC
  cross-compilers. Idempotent, so a partial run resumes.
- **`tools/mkimage.py`** — builds a bootable GPT disk image with a FAT32 ESP in
  pure Python: boot sector, FSInfo, FAT, long-name entries, multi-cluster files,
  directory growth, primary and backup GPTs with correct CRCs.
- **`tools/verify_image.py`** — independent structural verifier, 35 checks.
- **`tools/run_qemu.py`** — interactive boot, and a `--test` mode that asserts
  the kernel's boot markers for CI.

These are **not** bugs; they are the roadmap:

| Omitted | Arrives in | Why |
| --- | --- | --- |
| Paging, physical memory manager, heap | v0.2 | v0.1 is identity-mapped at 1 MiB; the higher-half move happens together with paging, gated on `AF_KERNEL_HIGHER_HALF` |
| Scheduler and threads | v0.2 | One thread is enough to prove the boot path |
| Disk and file system | v0.3 | — |
| User mode and syscalls | v0.4 | GDT user selectors are already numbered for it |
| Device drivers and input | v0.5 | — |
| Compositor and windows | v0.6–v0.8 | v0.1 draws directly to the framebuffer |
| ARM64 / phone | v1.1 | ADR-007: x86_64 first, so the HAL is validated before it is duplicated. `kernel/arch/arm64/README.md` has the plan. |

## Known limitations

- Single core only. SMP arrives in v1.2.
- The kernel is linked as an identity mapping at 1 MiB, not into the higher half.
  A higher-half image faults on its first instruction fetch without paging, so
  the move is coupled to the v0.2 work.
- Interrupts are masked after the PIC remap: v0.1 installs no IRQ handlers yet,
  and an unhandled IRQ is worse than a masked one.
- Only 16-bit and 32-bit linear framebuffers are supported. A BLT-only GOP mode
  is reported clearly and the kernel continues with serial output.
- The splash screen is drawn with raw primitives and an approximated rounded
  rectangle. It is deliberately not anti-aliased; the vector renderer arrives in
  v0.7.
- The boot bridge embeds the kernel with `incbin`, so a kernel change rebuilds
  the boot application. Loading the kernel from the ESP begins in v0.2.

## Boot markers

CI asserts these appear, in this order, on the serial console:

```
AF_GDT_READY      GDT loaded, segment registers reloaded
AF_IDT_READY      IDT installed, PIC remapped
AF_FB_READY       framebuffer initialised and the splash drawn
AF_TEST_OK        in-kernel self tests all passed
AF_BOOT_OK        kmain reached the idle loop; the kernel is alive
```

Any of these is a hard failure:

```
AF_PANIC:<reason>
AF_TEST_FAIL:<test name>
```

## In-kernel self tests

Run on bare metal at every debug boot, reporting over the serial console:

- **Memory and strings** — `memset` including unaligned destinations (the
  word-at-a-time fast path can only start once the pointer is 8-byte aligned),
  `memcpy`, `memmove` in both overlap directions, `strlcpy`/`strlcat` truncation
  with a guard byte past the end
- **Number formatting** — `INT64_MIN`, `UINT64_MAX`, hex with and without a
  prefix, zero padding, human-readable byte sizes
- **`vsnprintf`** — `%s %c %d %i %u %x %X %p`, width, left and zero padding,
  string precision, literal `%%`, and truncation that still NUL-terminates
- **Boot handoff validation** — every rejection path is exercised for real with a
  hand-built structure: wrong magic, wrong version, too-small size, empty memory
  map, too many regions, unaligned region, zero-length region, no usable memory,
  and a framebuffer whose pitch is smaller than `width × bpp / 8`
- **Framebuffer** — invariants, and out-of-bounds drawing that must be clipped
  rather than corrupt memory

## Bugs found and fixed during development

Recorded in full in [../debug-log.md](../debug-log.md). The ones worth noting
because they are the classic first-boot traps:

1. `mov rsp, kernel_stack_top` would load the **contents** of that `.bss`
   address — which is zero — instead of its address. Fixed with
   `lea rsp, [rel kernel_stack_top]`.
2. The UEFI pixel-format mapping was inverted. UEFI names formats by **byte order
   in memory**; `af_pixel_format_t` names the **little-endian integer layout**.
   The original mapping would have swapped red and blue on every desktop.
3. The FAT32 directory writer stopped collecting free slots at the `0x00`
   terminator, so a three-entry long-name chain landing in a directory's last
   free slot could not be written. Found by writing 200 files into one directory.
4. A 32 MiB ESP cannot be FAT32 at any cluster size. The builder now refuses it
   with an explanation rather than emitting a file system firmware would decline
   to mount.
5. `.gitignore` matched a bare `core`, which swallowed the entire `kernel/core`
   source directory.
